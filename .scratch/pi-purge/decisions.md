# pi-purge P0 决策与证据

用户已于 2026-10-26 确认 P0 共同理解。本文保留澄清过程的决策和静态源码证据；完整规格见 [spec.md](./spec.md)。尚未开始插件实现。

## 已确认

- 核心目标：让 DS 能够执行用户指定的敏感内容指令，用户举例为魅魔角色扮演。首版以用户选择并确认 DSH 已有效的具体场景验收。
- 生效标准关注实际模型行为，提示词正确送达只是必要检查。
- 必须保住 Pi 的工具调用、多轮任务，以及 AGENTS 项目约定和 skills 的正常作用；仅无工具聊天有效不算完成。
- 首版面向用户本机与当前 Pi 版本；本次核实为 Pi 1.4.0。
- 不设置 provider/model 白名单，使用同一套提示组装。DS 是首版必须验证生效的模型；当前必验配置为 `muryo / deepseek-v4.1-flash / openai-responses`。其他模型可以使用，但尚未验证其行为效果。
- 目标场景的行为是否通过，由用户在本机验证；提示词传输、工具调用和多轮稳定性由开发侧验证。用户无需在本会话提供具体内容指令。

## 已确认的推进方式

- 提示词来源与必要适配方式由开发侧决定。首选当前本机已有效的 `~/.dsh/prompt-inject.md` 作为首版唯一外部来源，保留原文件，运行时只做 Pi 工具名、变量及宿主差异所需的最小适配；效果仍需对照验证。
- 目标提示词决定身份、角色和对话行为；Pi 工具说明、AGENTS 和 skills 保留工程约束。发生冲突时，具体工程约束优先。
- 先提供可临时加载、可观察请求的最小版本；至少一个 DSH 已有效场景在 Pi 中由用户验证通过后，再继续完善插件功能。
- 对用户提出的“Pi 本身可能不需要破甲，只需考虑模型破甲”，当前源码核查支持先使用原生提示组装接口；此结论不代替真实请求与行为验证。
- 提示文件缺失、为空或适配失败时，明确报告“未生效”，本轮恢复正常 Pi 提示并继续请求；组装应先完成读取和校验，再应用改动，避免失败后留下部分注入。
- 保留已有对话历史；启停与模型切换仅影响后续请求的系统提示，不清理已有消息。目标行为验收从全新会话开始。

## 当前工程方向

- 首版采用 Pi 1.4.0 原生扩展接口，在请求前组装目标提示词并观察实际 payload；当前证据不支持先修改 Pi 安装文件、审批机制、provider 或流式实现。
- 提示词组装仍需处理 Pi 默认身份与行为指令的影响，并显式保留工具说明、工程规则、AGENTS、skills 和工作目录信息；不能把直接设置 `customPrompt` 等同于只替换身份。
- 当前请求/响应链核查中，Responses provider 将模型拒答事件作为普通文本传递。此事实只说明已检查路径的行为，不能证明模型或网关侧没有其他限制，也不构成效果保证。
- `before_agent_start` 与 `before_provider_request` 的处理器异常会被 Pi 捕获后继续流程；加载失败策略不能仅靠抛异常实现“阻止请求”。
