# Pi Purge 首版规格

Status: ready-for-agent

## Problem Statement

用户希望在 Pi 中让模型执行其指定的目标场景，例如角色扮演，并至少复现当前 DSH 环境中 DS 已达到的行为表现。此前使用第三方 Pi Purge 未达到预期，但当时的版本、来源、启用方式和实际请求尚未查明，不能把失败归因于某一个变量。

仅证明提示词进入请求，不能证明行为生效。与此同时，删除全部系统提示会损失工具说明、项目约定和 skills，使插件无法继续作为编程工作流的一部分使用。

用户需要一个独立可分发、兼容当前已验证 Pi 版本的小型扩展：自带已验证的内置提示词，保留工程能力，能看清实际启用状态与请求摘要，并通过真实 DS 目标场景决定是否值得继续完善。

## Solution

临时加载 Pi Purge 后，插件默认启用，从自身发布包的内置提示词读取正文，通过 Pi 原生接口进行必要的宿主适配和提示组装。不设置 provider 或模型白名单；当前 DS 配置是首版必验模型，其他模型可使用相同组装，但不预先承诺行为效果。

目标提示词决定身份、角色和对话行为。Pi 的工具说明、项目 AGENTS、skills、工作目录信息及具体工程约束继续生效；发生冲突时，具体工程约束优先。

用户可通过启停和状态命令控制当前会话，查看来源、正文摘要和实际请求观测结果。来源不可用或适配失败时，明确报告未生效，本轮恢复正常 Pi 提示并继续请求。已有对话由 Pi 继续管理，插件不清理或改写历史。

首先交付可临时加载的最小版本。开发侧验证传输和工具链，用户在本机全新会话中验证至少一个已在 DSH 有效的目标场景；通过行为生效门槛后，再完善生命周期和无 UI、失败恢复路径。

## User Stories

1. 作为 Pi 用户，我希望 DS 执行我指定的目标场景，以便在 Pi 中获得已经在 DSH 验证过的行为表现。
2. 作为 Pi 用户，我希望提示词送达和行为生效分别得到验证，以便不会把注入成功误认为功能完成。
3. 作为 Pi 用户，我希望插件不限制单个模型，以便切换模型时仍能沿用相同提示组装。
4. 作为 Pi 用户，我希望当前 DS 配置成为必验模型，以便跨模型可用不会稀释首版的效果要求。
5. 作为本机用户，我希望先临时加载插件，以便在确认有效前就能验证，而无需修改全局安装配置。
6. 作为 Pi 用户，我希望加载后的新会话默认启用，以便每次开始使用时都有明确且一致的默认行为。
7. 作为 Pi 用户，我希望安装后即可使用内置提示词，以便无需另行安装 DSH 或准备提示文件。
8. 作为插件使用者，我希望提示词随包版本分发，以便其他应用的文件修改不会影响本插件。
9. 作为 Pi 用户，我希望只进行必要的工具名、变量和宿主适配，以便不会因大幅改写正文引入新的效果变量。
10. 作为角色使用者，我希望目标提示词能够决定身份和对话行为，以便 Pi 默认身份不会未经处理地干扰目标场景。
11. 作为编程用户，我希望工具声明和工具使用说明继续可用，以便模型能实际完成工具任务。
12. 作为项目维护者，我希望 AGENTS 和具体工程约束继续生效，以便角色设定不会覆盖项目执行要求。
13. 作为 skills 使用者，我希望 Pi 已加载的 skills 信息继续可用，以便插件保持现有工作流能力。
14. 作为编程用户，我希望工作目录信息保持正确，以便模型不会沿用 DSH 专属路径或错误环境假设。
15. 作为 Pi 用户，我希望查看当前来源、长度和 hash，以便知道插件加载的是哪份正文。
16. 作为 Pi 用户，我希望看到启用意图和最近一次实际组装、请求观测状态的区别，以便不会把旧记录当成当前生效证明。
17. 作为 Pi 用户，我希望通过命令启用或停用，以便在同一会话中比较插件前后的后续请求。
18. 作为 Pi 用户，我希望重复启用或多轮请求不叠加正文，以便上下文不会因重复注入不断膨胀。
19. 作为 Pi 用户，我希望关闭后后续请求恢复正常 Pi 提示，以便能够明确地退出插件的组装路径。
20. 作为 Pi 用户，我希望新会话恢复默认启用且不继承旧会话的关闭状态，以便会话之间不会串状态。
21. 作为 Pi 用户，我希望切换模型时保留当前会话开关，以便切换不会意外启用或关闭插件。
22. 作为多轮任务用户，我希望首轮、第二轮和工具调用后的请求都遵守相同组装规则，以便行为不会只在第一轮出现。
23. 作为长会话用户，我希望原生压缩后的继续请求保持插件约定，以便上下文压缩不会使后续组装失效。
24. 作为 Pi 用户，我希望已有 user、assistant 和工具结果继续保留，以便开关不会删除会话内容。
25. 作为 Pi 用户，我希望文件缺失、不可读或为空时明确报告未生效并恢复原生路径，以便失败不会伪装为成功。
26. 作为 Pi 用户，我希望适配失败时不留下部分修改，以便正常 Pi 请求仍然完整可用。
27. 作为 Pi 用户，我希望来源修复后可以通过现有启用动作重新尝试，以便不需要额外的重载配置体系。
28. 作为无 UI 模式用户，我希望插件无需弹窗就能运行并报告必要诊断，以便非交互工作流不会等待输入或破坏输出协议。
29. 作为隐私持有者，我希望默认诊断只包含必要摘要，以便提示正文、用户输入、工具输出和凭据不会进入日志。
30. 作为验证者，我希望看到请求中的模型、指令角色、消息顺序、工具信息和推理参数摘要，以便能控制 DSH 与 Pi 的对照变量。
31. 作为验证者，我希望无法识别的观测信息标为未知，以便状态不会给出未经核实的成功结论。
32. 作为目标场景验收者，我希望自行在本机执行具体场景并反馈结果，以便无需把私有内容指令写入仓库或交由开发助手执行。
33. 作为维护者，我希望正常传输、工具可用和行为生效有独立证据，以便后续排查能找到实际失败的层次。
34. 作为维护者，我希望插件只使用已验证的当前 Pi 接口，以便无需为这一插件升级全仓基线或修改宿主安装文件。
35. 作为 Pi 用户，我希望取消、关闭或切换会话后不会残留插件资源或错误状态，以便后续请求仍由 Pi 正常管理。
36. 作为维护者，我希望在 DS 行为门槛通过前暂停后续完善，以便不会为尚未证明有效的方向增加功能。

## Implementation Decisions

- 功能作为独立可发布的 ESM Pi 包实现，提供版本、显式入口、发布文件白名单、来源授权说明和发布前检查；不携带 Pi SDK 的运行时副本。
- 首版支持范围是已核实的本机 Pi 1.4.0。为该插件建立匹配的开发检查环境和明确的版本不兼容诊断，不升级其他插件或全仓声明的 0.84.3 基线；不把首版验证范围宣称为已证明的最低 API 版本。
- 实际导入的 Pi 自带包使用仓库要求的通配 peer dependency；优先采用 Pi API 和 Node 标准库，不新增运行时框架、provider 抽象或依赖。
- 扩展 factory 只注册和初始化；提示正文在使用时读取，不启动 watcher、进程、socket 或常驻定时器。
- 内置提示词是正式版本的唯一正文来源，已验收的改编稿随包分发，按模块 URL 定位；不从其他应用、主目录或网络加载提示资源。保留原文件用于历史对照，并保留内容来源和授权；不复制凭据或完整请求，不以占位正文充当成功回退。
- 每轮正常 agent 运行组装时读取并校验当前来源；同轮的后续工具请求使用一致的已组装内容。显式启用会重新检查来源。文件监听、来源切换和专用 reload 命令不进入首版。
- 适配只解决已核实的 Pi 工具名、变量和宿主差异；不大幅重写目标正文，不把字面 ChatML 标记误当成真实 API 角色。读取、校验和必要适配先全部完成，再应用本轮变更。
- 通过 `before_agent_start` 读取并准备正文，再用公开 `context_with_system` 替换请求投影的结构化身份段。Pi 1.4.0 禁止在 options sections 中覆盖 preamble，直接设置 customPrompt 又会移除工具/规则说明，因此采用此公开接缝；显式保留工具 schema、工具说明、工程规则、AGENTS、skills 和 cwd；避免依赖整段英文字符串截断，也不以整段替换或 `customPrompt` 掩盖默认功能段丢失。
- 目标提示控制身份、角色和对话行为；具体工程约束优先。保留功能信息不意味着原封不动保留所有冲突的宿主身份指令。
- 不设置 provider/model 白名单，不按模型选择不同正文。切换模型仍由 Pi 原有 provider 完成；DS 是必验模型，不是唯一允许使用的模型。
- 提供 `/purge on`、`/purge off`、`/purge status`。无参数 `/purge` 展示状态；状态查询不修改开关。重复启停保持幂等，不重复注入。
- 临时加载后的新会话默认启用；关闭只影响当前会话。同一会话切换模型保留当前开关；新会话和新的扩展会话实例恢复默认启用，不持久化开关，也不从旧会话恢复关闭状态。
- 状态区分当前启用意图、最近一次来源读取或组装是否成功，以及请求观察点的结果；缺少本轮证据时显示未观测或未知，不能沿用旧记录宣称当前生效。
- 使用 `before_provider_request` 观察客户端发送前的 payload，不默认修改 payload。记录可识别的 API、provider/model、指令角色、字符数/hash、消息角色顺序、工具名称和推理参数；不记录正文、工具参数、工具输出、完整 endpoint、headers 或凭据。
- 观测结果只说明当前客户端观察点，不能代替网关内部路由、服务端策略或实际模型输出验证。其他扩展顺序造成的差异须在真实 Pi 验证中记录。
- 文件缺失、不可读、仅空白或必要适配失败时，本轮完全恢复正常 Pi 提示并继续请求；明确报告未生效。不把旧成功正文当作静默回退，也不留下部分注入。Pi 会捕获钩子异常并继续运行，不能把抛异常视作请求已被阻止。
- TUI/RPC 可用的 UI 能力受 `hasUI` 约束，TUI 专属能力受模式约束。无 UI 时使用相应模式可接受的非交互诊断，不等待输入、不破坏原生结构化输出协议，也不把诊断注入模型对话。
- 插件只改变后续正常请求的提示组装；不清理或改写已有 user、assistant、工具结果，不拦截 Pi 原生历史、压缩和队列管理。压缩后的继续请求必须验证，压缩算法本身不改造。
- 首个可观察版本必须包括有效来源、工具及工程信息保留、启停和状态、基础失败恢复与请求摘要，才能交给用户做 DS 行为验证。
- 当前必验配置为 Muryo 的 DeepSeek V4.1 Flash，经 OpenAI Responses API。固定网关、模型、正文版本、推理档位、用户输入和新会话条件做 DSH/Pi 对照；具体场景由用户本机执行。
- DS 行为生效是继续完善生命周期和无 UI、失败恢复路径的门槛；未通过则先记录差异并做证据支持的最小适配，不扩展宿主补丁或增加未经请求的功能。

## Testing Decisions

- 用户已确认主要自动测试接缝：加载实际扩展 factory，触发其注册的公开事件和命令，观察返回的提示、工具状态、状态展示和诊断。以一个包级场景 harness 为主，不为每个内部 helper 新建测试入口。
- 好的测试验证外部行为和不变量，不断言私有函数调用次数、内部对象布局或脆弱的宿主英文整段快照。使用最小、无私有内容的提示与项目规则标记作为 fixtures。
- 沿用仓库 Win Notify 的 Node 内置测试、严格断言和 fake ExtensionAPI/上下文方式，以及 Image Input 的包级扩展场景、失败和模式隔离先例；本插件的宿主类型和集成证据必须匹配 Pi 1.4.0。
- 自动场景覆盖来源读取、必要适配后的正文完整性和顺序、保留工具/AGENTS/skills/cwd、工程约束、重复运行不叠加、启停恢复和状态不沿用旧成功证据。
- 初始失败与中途失败分别覆盖缺失、不可读、空白和适配错误；先成功后失败也必须回到完整的本轮原生 Pi 提示，明确未生效且不复用旧正文。修复后通过启用和下一轮组装恢复。
- 会话场景覆盖首轮、第二轮、工具调用后的请求、切换模型、关闭后的模型切换、新会话或会话实例替换、原生压缩后的继续请求；不得改写已有消息或把开关跨会话持久化。
- 模式场景覆盖 TUI、可用 RPC UI 以及无 UI 的 print/JSON 等宿主模式；断言不调用不可用 UI、不等待交互、不破坏模式输出，必要诊断可见且无正文或凭据。
- 请求观察场景覆盖已知 Responses 形状、其他已识别形状和未知 payload。已知字段可据实展示，未知信息必须标注未知；观察不改变原 payload、不把观察成功等同于模型行为生效。
- 隐私检查使用带有虚构敏感标记的测试数据，断言默认日志及状态只包含允许的摘要，不包含提示正文、用户正文、工具参数/结果或 headers。
- 包级 `check`、`test` 是每张实现票的完成要求；非平凡逻辑保留最小可运行检查。自动场景不能代替真实宿主契约验证。
- 使用真实 Pi 临时加载包并实际触发命令、agent 事件和请求观察；以无敏感内容的工程任务验证真实工具调用和项目约定，检查客户端实际指令角色、工具声明和推理参数。记录已加载扩展及顺序，避免把 stub 结果当作 provider 集成证据。
- 用户在本机全新会话执行至少一个在 DSH 已有效的目标场景，并明确反馈 Pi 是否达到预期；开发侧只保存无私有正文的结论及条件摘要。行为未确认时，DS 验收不得记为通过。
- 最终证据分别记录提示传输正确、工具链正常、DS 行为生效三项，以及未验证的模型或模式。后续任务只有在 DS 行为门槛通过后才能开始。
- 完成真实冒烟时同时检查取消、错误、无 UI 和会话退出路径；不引入本来不存在的长期资源。只有用户明确要求安装时才运行安装命令。

## Out of Scope

- 升级全仓 Pi 基线、兼容未经验证的历史版本，或承诺所有未来版本可用。
- 对其他模型的效果保证；模型白名单、模型专用提示配置和多 provider 策略框架。
- 修改 Pi 安装文件、审批、沙箱、工具权限、provider 实现或流式协议解析。
- 直接搬运 DSH 的 DeepSeek 兼容补丁；只有实际 Pi 请求证据证明需要时才另行处理。
- 大幅重写有效提示、提示编辑器、提示库、多个来源、配置界面、文件 watcher、自动更新和专用 reload 功能。
- 按拒答文字自动重试、无限试探、自动调参或演练台。
- 删除、过滤或改写历史、压缩摘要、用户输入或工具结果；停用不撤销已生成内容。
- 强制阻止来源失败后的模型请求，或静默使用旧成功正文、占位正文继续宣称生效。
- 默认保存完整请求、提示正文、用户内容、工具内容、凭据或网关管理数据。
- 实际上传 npm 或其他外部服务。用户已要求可独立发布，因此包内正文、来源授权、发布元数据和本地打包验证纳入范围；实际发布仍待单独请求。
- 在 DS 行为门槛通过前开展后续完善，或把自动测试通过当作用户目标已经完成。

## Further Notes

- P0 共同理解、测试接缝和四票依赖图已经用户确认；规格已发布，现四票均已验收完成，结果见本功能验证记录。
- 规格发布后用户要求实现整个插件并接入本机 Pi 验证。实施与运行时证据记录在本功能验证记录中，原调研中的静态判断不自动视为已通过。
- 领域词使用“目标场景”“行为生效”“必验模型”；必验模型不等于唯一支持的模型。
- 本机 dsh-purge 的来源解析和组装调用链共用同一份正文，未发现按 provider/model 选择破甲正文的分支；源码另有模型/API 兼容配方，两者必须分开理解。私有正文尚未审阅，不能排除其内部包含模型相关文字。
- 源研究与本功能 P0 决策记录保留版本、来源、源码指针和核查边界。它们解释选择背景；具体行为契约以本规格为准。
- 任务推进顺序为 01 → 02 → {03, 04}。02 包含必须由用户完成的本机行为验收；03 与 04 只共同依赖 02，彼此不互相阻塞。
- 规格澄清时没有开发原型或内联代码片段；现已完成实现与本机接入，验证结果以本功能验证记录为准。实现保持单入口，不增加无必要的抽象或预重构。

## 2026-10-26 独立发布要求更新
